# GFX Agent Guidance

Read the repository [AGENT.md](../../../AGENT.md) first. This file records gfx-specific contracts and source entry points.

## Abstraction Boundaries

- `hitagi::gfx` unifies DX12, Vulkan, and Metal through `gfx.base`; `gfx.mock` supports CPU-side tests. `gfx::create_device()` selects the backend. The `gfx` aggregate exports the base API, render graph, utilities, `GraphicsFrameSystem` (`graphics_frame.cpp`) and `gfx::GraphicsPlugin` / `gfx::GraphicsContext` (`plugin.cpp`). Its plugin partition imports app; app does not import gfx. GraphicsContext contains no asset types; callers explicitly assemble asset loading contexts. The frame system borrows Device/CommandQueues and accepts a host-supplied `ecs::Group`; app owns the frame-stage enum; GraphicsPlugin owns registration policy.
- `hitagi::rg` describes resource accesses and pass dependencies. Its public concepts are resources, passes, and access edges. A gfx View is an execution object for an access, not a separate graph node.
- `GPUBuffer` owns byte storage; `GPUBufferView` describes a range and element layout. Multiple views may overlap. Creating a view must not rearrange stored data.
- Keep binding, mapping, and descriptor ownership with gfx objects; keep dependency construction, scheduling, and retention through GPU completion with the graph. Reuse gfx descriptions without duplicating their field definitions in rg.

## Source Entry Points

Each named module keeps one aggregate `.cppm` and uses `.cpp` interface partitions, following asset's organization. Partition filenames follow the layout before `68d48b5c`. Export declarations with `export namespace`; place out-of-class implementations and internal helpers in ordinary named namespaces. Do not add implementation directories, `impl.cpp`, or per-partition `.cppm` files. Complete classes live in their responsibility-specific files; `dx12_types.cpp` / `vk_types.cpp` / `metal_types.cpp` contain forward declarations only. `RenderGraph` lives in `render_graph.cpp`, together with methods that assemble nodes/builders through the complete graph definition. Inspect module declarations rather than inferring a file's role from its extension.

Static resource factories are defined in the ordinary module implementation unit [base/resource_creation.cpp](base/resource_creation.cpp). It imports the backend interfaces without making the base interface depend on them. Do not move those definitions into a base interface partition, which would introduce a module dependency cycle.

External dependency modules are provided by the independent `hitagi_interop` target in [interop/XMake](../../interop/xmake.lua), named `interop.<library_name>`. [interop.fmt](../../interop/fmt.cppm) and [interop.spdlog](../../interop/spdlog.cppm) export their respective library entities; import fmt explicitly when using it, since spdlog does not re-export it. Windows-only [interop.dx12](../../interop/dx12.cppm) exports DX12/DXGI/WRL entities and typed macro adapters in `hitagi::interop`; the separate [interop.d3d12ma](../../interop/d3d12ma.cppm) exports the allocator library. These modules must not import engine modules. [interop.vulkan](../../interop/vulkan.cppm) and [interop.magic_enum](../../interop/magic_enum.cppm) re-export the official upstream modules without copying their implementations. Keep `VULKAN_HPP_NO_CONSTRUCTORS` and platform definitions public so producers and importers agree. Do not reintroduce Vulkan-Hpp textual includes alongside that module. [interop.vma](../../interop/vma.cppm) exports VMA declarations; its sole implementation is [interop/vma.cpp](../../interop/vma.cpp), not a public module source. Tracy types come from `interop.tracy`, `interop.tracy.vulkan`, and Windows-only `interop.tracy.dx12`; its [thin macro header](../../interop/tracy_macros.hpp) preserves call-site scope, source locations and disabled argument elision without including Tracy headers. Consumers must not include VMA or Tracy headers directly. Raw Vulkan C entities are also exported by `interop.vulkan`; `interop.sdl`, `interop.win32`, and `interop.slang` cover the remaining native APIs. Only the thin `win32_macros.hpp` retains call-site COM type deduction. Vendor SDK headers must not be included in gfx consumers.

## Resource, View, and Binding Contracts

- Resources retain their descriptions through `ResourceWithDesc`, but do not retain an abstract `Device` or expose `GetDevice()`. Use the resource type's static `Create` method; the assembly boundary selects the backend and validates native ownership before injecting concrete dependencies.
- Backend resources depend on the native device, allocator, binding facilities, logger, or compiler that they actually use, not the complete backend Device. Texture initialization that needs command submission is assembled in `resource_creation.cpp`; allocation and mapping behavior remain backend responsibilities.
- Device owns native bootstrap state, allocators, and capabilities. The GraphicsContext resource installed by GraphicsPlugin owns `CommandQueues`, bindings, and the shader compiler as direct members, created after Device and destroyed before it. Consumers receive explicit references; low-level resources must not receive this owner as a service locator. Tests must provide the same lifetime ordering.
- Queues own execution synchronization and profiling state; Vulkan queues also own their command pools. Command contexts and submitted resources must not outlive the facilities they reference. Bindings must outlive all views and samplers using their handles.
- `GPUBufferDesc::size` is a byte count. `element_size`, `element_stride`, and binding offset alignment have different meanings. A zero ViewDesc stride means tightly packed elements; Storage usage does not imply record padding.
- Query storage binding constraints with `GPUBuffer::GetStorageViewRequirements(device)` when planning independently bound ranges. Backend differences stay behind that API; the caller determines data placement.
- `MappedSpan<T>` is created only by `view.GetMappedSpan<T>()`. It follows the View's explicit stride, validates mapping/type constraints, and unmaps through RAII. It does not construct a temporary View from a Buffer. Keep its underlying storage alive throughout the mapping.
- Strided mappings are not necessarily contiguous. Use indexed/element-wise access when needed; `data()` rejects non-contiguous multi-element spans.
- Vulkan bindless creation resolves native handles from the buffer ViewDesc or existing TextureView/Sampler; callers do not pass redundant raw handles or device addresses. The complete heap/indexing classes and their definitions live in `vk_resource.cpp`; `vk_bindless.cpp` keeps the facade declarations and shared handle management, while construction, destruction and backend dispatch are defined in `vk_resource.cpp` to avoid a module cycle; they cast shared resource pointers with `std::static_pointer_cast` and View/Sampler references with `static_cast`.
- Buffer/texture views and samplers own their bindless handles. Resolve a graph handle, then use the object's `GetBindlessHandle()`; do not add a parallel PassNode binding API.
- GPU use can outlive CPU command recording. Resources, views, samplers, and descriptors must remain alive until their GPU work completes. Graph retention supplies this for graph accesses; direct gfx callers must provide it. A non-owning reference is valid only while its owner's lifetime is guaranteed.
- Texture attachment descriptors belong to Views: `DX12TextureView` owns RTV/DSV descriptors and `VulkanTextureView` owns its image view.
- Record arrays normally use one View/descriptor with shader indexing. `BindlessMetaInfo` carries a handle, record index, and stride; preserve the CPU/Slang ABI when changing it. Independent binding alignment does not determine the stride inside an already bound array.
- Shaders use Slang modules compiled to DXIL/SPIR-V. `ShaderCompiler::LoadProgram` creates a target-specific session snapshot; `ShaderProgram::Compile` composes, optionally specializes by type, and links an entry from the last module. Load in-memory dependencies before importing modules; file modules resolve through search paths, so a material module can precede the file shell it imports. Programs retain their compiler state; Slang calls and session destruction are serialized through that state's mutex. GPU resource factories currently load a program per shader; callers of the program API can reuse a session across entries.
- Vertex inputs come from Slang reflection for the actual target, not a separate DXIL compile. Vulkan preserves reflected input locations and entry names. `bindless.slang` imports Slang's typed `DescriptorHandle<T>` facilities; Vulkan maps the standard non-mutable bindings in set 0 onto descriptor heaps when supported, otherwise onto a shared update-after-bind descriptor set (sampler 0, sampled image 2, storage image 3, storage buffer 7). Both paths preserve BindlessHandle and BindlessMetaInfo. The shared storage path still uses raw byte-address buffers and the 16-byte CPU handle ABI. Integer ID textures use integer loads rather than filtered sampling.
- The build uses Slang headers/library/runtime from the installed Vulkan SDK (validated with SDK 1.4.363.0, Slang 2026.17-25-gc7954ebd1). DXC is only a downstream DXIL dependency. Cook format v3 stores ordered modules and specialization types; older cooked assets require re-cooking. Runtime imports still require their source modules on disk.
- Graph materials use interfaces/specialization: a generated module implements the shell's `IMaterial`, and every stage entry is generic over it. Renderer shells mirror CPU frame/instance/draw records by hand; `GenerateShaderStruct` remains for material data. Reflection-based record-layout validation is separate follow-up work.
- `shader_layout.cpp` describes that raw 32-bit storage ABI: derive fields from CPU types/offsets and generate shader declarations through `GenerateShaderStruct`. It is not constant-buffer packing. Renderers own field semantics; gfx owns resource-handle wrappers and layout generation.

## Render Graph Contracts

### Declaration and Resolution

- Declare/import resources and declare their pass accesses before `Compile()`. Physical resources are instantiated lazily; access Views are prepared for execution. Executor callbacks must not mutate the compiled graph or bypass its declared resource dependencies.
- Resource handles identify graph resources. `GPUBufferEdgeHandle` and `TextureEdgeHandle` identify a particular pass-owned access. `pass.Resolve(resource)` returns the resource; `pass.Resolve(edge)` returns that access's View.
- Render/Compute buffer and texture access declarations return edge handles. Configuration setters, sampler declarations, Copy operations, and Present declarations return `void`. Render/Compute/Copy `Finish()` returns a pass handle; Present `Finish()` returns `void`. Keep these builders non-fluent.
- Edges retain gfx ViewDesc values; the physical resource pointer must be empty at declaration because the graph resource handle is authoritative. An edge holds at most one View. Copy accesses need no View, and samplers need no invented SamplerView.
- Multiple accesses to one resource remain dependencies on that resource. Compatible access requirements are merged for barriers; conflicting read/write or texture layouts within a pass are rejected. Synchronization currently has whole-resource granularity.
- Repeating an identical access in one pass reuses its edge handle and View, merging pipeline stages. Different ViewDesc ranges, types, names, or external View identities remain distinct; handles still belong to one pass. This avoids allocating duplicate Views without weakening access validation.
- `RenderPassBuilder::Read(shared_ptr<TextureView>, stage)` imports the View's external texture and declares a shader read using that same View. The View must be non-null and ShaderRead; the edge retains it through GPU completion, and `pass.Resolve(edge)` returns the original View. Dependencies, culling, conflict validation, and barriers use the imported resource node. This overload reads the original import node, not a later `MoveFrom()` node.
- `MoveFrom()` creates another graph node for the same physical resource and expresses subsequent use, such as drawing an overlay onto a prior output. It does not provide cross-frame history storage.

### Compilation, Execution, and Lifetime

- Compile keeps enabled Present passes and passes marked `AllowPassCulling(false)`, then traces their dependencies and sorts the graph. Extraction helpers create non-cullable passes, so offscreen graphs can execute without Present. A graph with no retained output can be fully culled.
- Call `Execute()` only after successful `Compile()`. Current CPU command recording is serial. Submission uses per-queue fences; Execute waits for this execution's latest submissions before retirement/reset. Do not describe this as parallel recording or only waiting for the previous frame.
- A RenderGraph object may be reused across frames. Reset clears passes, transient nodes, and dependency edges, but retains original `Import()` nodes until `ClearImportedResources()`. `MoveFrom()` aliases are frame-local even when they reference imported resources; retire them after execution and clear the retained import's move link so it can be moved again next frame.
- Resource handle slots have no generation counter. Do not reuse transient handles after reset or imported handles after clearing imports. Access handles are specific to their owning pass.
- The transient pool reuses compatible complete resources across frames; it is not within-frame physical memory aliasing. Texture compatibility includes the actual clear value (color or depth/stencil), because render attachment clearing reads the physical resource description. Imported and moved resources are excluded from pooling.
- Graph construction/mutation is currently single-threaded. Pass identity generation also uses a shared non-atomic counter, so even separate graphs must not create passes concurrently. Supporting that requires an explicit concurrency design; a counter alone would not make graph mutation thread-safe.

## Backend and Synchronization Constraints

- `Transition()` both updates tracked resource state and returns the barrier to emit. Do not discard it or call it speculatively.
- Command contexts require `Begin()` / `End()` around recording. Submit each context to a matching Graphics, Compute, or Copy queue.
- Acquire the swapchain image before using it. The Vulkan queue/swapchain implementation manages its binary semaphores; avoid duplicating that management in callers.
- Vulkan resize passes the current swapchain as `oldSwapchain` and retains retired swapchains and their present semaphores until a fence on reacquisition proves the replacement's first presentation has completed. Further resizes carry pending retirements forward. Do not destroy the displayed chain before its replacement presents, or use device-idle alone as proof that the presentation engine has released its resources. Prefer opaque surface composition for ordinary application windows.
- Enable and configure Vulkan validation layers externally with Vulkan Configurator; the engine does not request instance layers. Debug builds retain the debug-utils message logger. For performance captures, disable layers in Vulkan Configurator and verify loader logs or sampled stacks. Queue lock/driver submit timings are separate Tracy plots, and SDL modal frames have their own CPU zone.
- Queue selection is implemented in the Vulkan backend. One universal family supplies up to three native queues; Graphics uses index 0, Compute uses index 1 when available, Copy uses index 2 when available and otherwise shares Graphics. KosmicKrisp exposes one queue, so all three logical queues share it. Device owns unique native queue states; wrappers across all CommandQueues groups borrow/share those states. Submit, Present, Tracy initialization and idle waits synchronize through the same native queue mutex. Device-wide idle locks unique queues in creation order. Command pools stay with logical queues.
- `VulkanNativeQueue` lives in [vk_command_queue.cpp](vulkan/vk_command_queue.cpp). Native command-buffer submission data is extracted in [vk_command_buffer.cpp](vulkan/vk_command_buffer.cpp), avoiding a queue/resource module cycle. Do not hard-code family indices in callers. Aliased logical queues do not promise independent progress: submit producers before dependent waits, as the current graph does; preserve semaphore and resource memory dependencies.
- Metal uses official metal-cpp 26 through `interop.metal`. Its sole private implementation is `interop/metal.cpp`; consumers must not define the upstream implementation macros. The shared Slang SPIR-V is lowered to MSL 4 through `interop.spirv_cross` inside the resource partition; binding offsets and capacities live in `metal_configs.cpp`.
- Metal's native `MTLDevice` can be shared by multiple engine devices. Resources, bindings, and queues borrow the owning `NS::SharedPtr<MTL::Device>` by reference; its address preserves logical-device ownership checks without retaining a complete `MetalDevice` service locator.
- Metal queues batch command buffers and enqueue shared-event waits/signals on the GPU; Submit never waits for completion on the CPU. MetalFence owns a native MTLSharedEvent. Pending submissions retain completed recordings and dependency events until the queue completion value passes, reclaimed on Submit/NewFrame/WaitIdle. A recording owns its allocator, argument table, residency set, pipeline states, native resources, immutable bindless snapshots, and chunked metadata uploads. Re-recording allocates a separate recording while the previous one is in flight; an exclusively owned recording may reset and reuse its allocator and upload buffers. Bindless snapshots are shared until the table changes; per-draw metadata never copies the table. Sampler capacity remains 500,000. Sampled and storage images use distinct argument-buffer regions, including signed/unsigned variants. Queue-stage barriers order encoder work; shared events order cross-queue dependencies. The common RenderGraph still waits at the end of Execute; this backend change does not introduce cross-frame resource reuse without fences.
- Vulkan prefers descriptor heaps and falls back to descriptor indexing with partially-bound, update-after-bind and update-unused-while-pending bindings. `VulkanBindlessUtils` owns the shared handle pools and selects a variant of `VulkanDescriptorHeap` / `VulkanDescriptorIndexing` once at creation. Each implementation owns its descriptor storage, writes, binding, shader/pipeline configuration and metadata push operations; pipeline callers do not branch on the binding mode. The indexing implementation owns a common pipeline layout and uses ordinary push constants; descriptor capacities are checked against device limits. Views and samplers retain the native objects referenced by descriptors; a slot may be recycled only after its GPU users finish. Consult [vk_configs.cpp](vulkan/vk_configs.cpp), [vk_device.cpp](vulkan/vk_device.cpp) and [vk_bindless.cpp](vulkan/vk_bindless.cpp) for requirements.
- Vulkan device selection checks `shaderDrawParameters` and logical-device creation explicitly enables it. Slang-generated vertex shaders can declare SPIR-V `DrawParameters`; a supported API version alone does not enable this feature.
- DX12 uses a device-local Agility SDK factory/configuration. Do not reintroduce process-wide device/debug configuration as a workaround.
- DX12 window swapchains use `DXGI_SCALING_NONE`: an old back buffer must not be distorted to a newly resized window while awaiting the next present. PlatformHost/App supply live modal-resize frames; the graphics backend must not drive simulation or poll native events.

## Changes and Verification

- For shared API changes, trace DX12, Vulkan, Mock, graph callers, and shader consumers as applicable. Keep backend-specific behavior behind the shared contract.
- For resource/handle changes, verify ownership, stale or wrong-pass handles, range/stride interpretation, overlapping accesses, and GPU retention where affected.
- For backend or shader behavior, Mock-only tests cannot establish GPU correctness. Use relevant backend tests and shader compilation, and report unavailable coverage.
- gfx tests are part of the root `unit_tests` target. Use `--gtest_list_tests` and filter actual suite names; follow the root build/validation guidance.
- Update this file when contracts or source entry points change. Keep mapping tables and implementation inventories in source rather than duplicating them here.

- `GraphicsFrameSystem` begins the device frame on the calling thread. The host must call `Device::EndFrame()` after the full frame on that same thread, including on exceptions; App's RAII frame guard does this even if schedule preparation fails before BeginFrame. EndFrame is non-throwing and safe without an active frame. It does not wait for GPU completion. MetalDevice owns the per-frame autorelease pool behind BeginFrame/EndFrame; App must not import Apple pool types. Do not drain the device-lifetime fallback pool from either frame method: SDL live-resize callbacks may have younger native pools above it. Pools must unwind in stack order. Initialization, frame-external work and other threads need their own lifetime boundaries.
